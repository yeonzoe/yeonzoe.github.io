# How I Work — 작업 방법론

> 13년차 QA 엔지니어가 AI 보조 개발(vibe coding) 환경에서 **품질과 속도를 동시에** 잡는 방식.
> 실제 작업 레포의 규칙(`rules/`), 140+ 세션 핸드오프, 1,800+ 커밋에서 추출한 실행 원칙입니다.
> *(회사 내부 식별자·미공개 수치·내부 시스템명은 제외했습니다.)*

---

## 1. 작업을 두 축으로 분리해 관리한다 — 규모(Level) × 성격(Change Class)

모든 작업을 시작 전에 **두 개의 독립 축**으로 분류합니다.

**규모 (Work Level)** — 파일 수 기준
| 레벨 | 범위 | 조치 |
|---|---|---|
| L1 | 조회만 | 즉시 진행 |
| L2 | 1–2개 파일 | 간단 계획 |
| L3 | 3–5개 파일 | 상세 계획 |
| L4 | 6개+ 파일 | 상세 계획 + 승인 |

**성격 (Change Class)** — 구조를 바꾸는가?
| 분류 | 정의 | 행동 |
|---|---|---|
| L-구조 | 저장 방식·데이터 모델·통합 패턴·파일 구조 변경 | **반드시 사전 승인** |
| L-부분 | 기존 구조 안의 수정 | 바로 진행 |
| L-질문 | 요구사항이 모호 | **질문으로 해소** |

**왜** — 규모(L2)는 작지만 성격(L-구조)은 위험할 수 있습니다. 두 축을 섞으면 "작은 수정"이라며 저장 구조를 바꾸는 사고가 납니다. 분리하면 각각에 맞는 통제를 적용할 수 있습니다.

---

## 2. 합의된 구조는 잠근다 — Structure Lock

```
1. 설계   — 아키텍처 정의 (구조 확정)
2. 잠금   — 이후 L-부분 / L-질문만 허용
3. 개발   — 잠긴 구조 안에서만 작업
4. 해제   — 사용자가 L-구조 변경을 명시 요청해야 해제
```

**왜** — 한 산출물에서 저장 메커니즘을 3회 임의 변경 + 미요청 기능 6개가 누적되어 코드가 비대해진 적이 있습니다(전체 롤백으로 복구). 그 이후로 **구조는 합의 시점에 잠그고, 기술적 문제도 임의 변경 대신 보고 후 승인**을 받습니다.

---

## 3. SPEC → Plan → 실행 — 바이브 코딩 금지

L3 이상 작업은 **곧장 코딩하지 않습니다.**

```
SPEC(요구사항·구조 정의) → Plan(파일·변경 목록) → 승인 → 구현 → 검증 → 회고
```

**왜** — AI가 코드를 빠르게 쏟아낼수록, "무엇을 왜 만드는가"의 합의가 없으면 방향이 어긋납니다. SPEC을 먼저 고정하면 AI의 생산성을 살리면서도 표류를 막습니다. *(요구사항 정리 요청을 코드 작성으로 변환하지 않는 것도 같은 원칙)*

---

## 4. 세션은 핸드오프로 잇는다

L2 이상 작업이 끝나거나 세션이 끝나면 **핸드오프 문서**를 남깁니다 — 완료 내용 / 남은 TODO / 다음 세션 시작 방법 / 핵심 구조 / 관련 파일. (현재까지 140+건 누적)

**왜** — AI 세션은 컨텍스트가 리셋됩니다. 핸드오프가 있으면 다음 세션이 "어디까지 했고 무엇을 알아야 하는지"를 즉시 복원해, 긴 작업도 끊김 없이 이어집니다. 단일 진입점(SoT) 한 문서에 요구사항·미해결 질문·결정 이력을 모읍니다.

---

## 5. FP/FN 크로스 리뷰 — 과잉과 누락을 동시에 막는다

중요 산출물은 **두 관점의 서브에이전트를 병렬로** 돌립니다.

- **FP(False Positive) 리뷰** — 과잉·중복·근거 없는 것 / *잘못 구현된 것을 찾는다*
- **FN(False Negative) 리뷰** — 누락된 규칙·엣지케이스·일관성 결여 / *빠진 것을 찾는다*

**왜** — 한 방향 리뷰는 한쪽 오류만 잡습니다. 과잉(FP)과 누락(FN)은 성질이 반대라, 두 관점을 동시에 적대적으로 돌려야 사각지대가 사라집니다. 실제 대시보드 작업에서 한 단계에 12건의 정정 항목을 이 방식으로 잡아냈습니다.

---

## 6. 안전은 자동 가드로 강제한다

사람의 주의력에 의존하지 않고, 위험 동작을 **자동 차단 훅**으로 막습니다.

- **Production CUD 차단** — 생성/수정/삭제 테스트에 `skipOnProd` 가드가 없으면 경고
- **배포 ID 고정** — 새 배포 생성을 막아 공개 URL을 불변으로 유지
- **버전 동기화** — 배포 전 버전 표기 3곳을 자동 일치
- **비파괴 원칙** — 기존 데이터·스키마는 보존, **추가만** 허용

**왜** — "조심하면 된다"는 통하지 않습니다. 상용 환경 데이터 파괴, 중복 배포 같은 비가역 사고는 **사람이 아니라 가드가** 막아야 합니다.

---

## 7. 검증 없이 "정상"이라 말하지 않는다 — 증거 기반

"정상 동작합니다"라고 주장하기 전에 **end-to-end 증거**를 확보합니다. 배포는 push → 버전 → 배포 → 실제 화면 확인이 한 세트이고, 데이터 변경은 라이브에서 round-trip(쓰기 → 다시 읽기)으로 검증합니다.

**왜** — 검증 없는 "정상"은 가장 비싼 거짓말입니다. 토큰 비용보다 사람 시간이 비싸므로, 확신이 설 때까지 반복 검증하는 편이 결과적으로 빠릅니다.

---

## 8. 실수는 메모리로 자산화한다 — 피드백 루프

반복되는 실수·확정된 결정·검증된 패턴을 **영속 메모리**에 기록하고, 다음 작업에서 자동으로 참조합니다. (예: "테스트케이스 vs 체크리스트 혼동 금지", "저장소 전환 시 안전 순서" 등)

**왜** — 같은 실수를 두 번 하지 않는 가장 확실한 방법은 규칙을 코드/문서 밖의 **재사용 가능한 메모리**로 만들어 두는 것입니다. 개인의 경험이 팀과 다음 세션의 자산이 됩니다.

---

## 한 장 요약

| 무엇을 | 어떻게 |
|---|---|
| 작업 관리 | 규모(L1–L4) × 성격(L-구조/부분/질문) 2축 분리 |
| 구조 보호 | Structure Lock — 합의 후 잠금, 명시 승인만 해제 |
| AI 활용 | SPEC → Plan → 실행 (바이브 코딩 금지) |
| 연속성 | 세션 핸드오프 + SoT 단일 진입점 |
| 리뷰 | FP/FN 서브에이전트 병렬 크로스 리뷰 |
| 안전 | 자동 가드 훅 + 비파괴(추가만) |
| 신뢰 | 증거 기반 검증, "정상" 주장 금지 |
| 학습 | 영속 메모리 피드백 루프 |
