# Case Study — QA 운영 대시보드 + 데이터 무결성

| | |
|---|---|
| **회사 / 도메인** | 직방 (PropTech) |
| **역할** | QA Engineer (설계·구현·운영) |
| **기간** | 2024 ~ |

> *회사 내부 식별자(배포 ID·필드 번호·내부 경로)·미공개 수치는 제외하고, 접근 방식과 공개 가능한 성과만 기술합니다.*

---

## 배경 (Problem)

스프린트별 TC 현황이 여러 곳에 흩어져 있었고, 테스트 결과를 팀에 공유하는 데 매번 시간이 들었습니다. 또한 운영 중인 데이터를 다루는 도구였기에 **데이터 무결성**이 핵심 리스크였습니다.

## 접근 (Approach)

스프린트 TC 현황을 **실시간으로 한 화면에서** 추적하고, git·시트·이슈 트래커를 끊김 없이 잇는 대시보드를 설계했습니다. 운영 도구인 만큼 모든 변경에 **비파괴 원칙**을 적용했습니다.

1. **단계별 마이크로 배포** — 큰 변경을 작은 단계로 쪼개, 각 단계를 **동일 배포 ID에 갱신**하며 라이브에서 검증
2. **작업 사이클 고정** — `접점 매핑 → 적대적 3-lens 검증 → 정정 → 배포 → 라이브 round-trip 검증`
3. **비파괴 원칙** — 기존 데이터·시트 스키마는 보존하고 **추가만**. 스키마는 합의 후 잠금
4. **SoT 단일 진입점** — 요구사항·미해결 질문·결정 이력을 한 문서에 모아 표류 방지

## 방법 디테일 (How) — 데이터 무결성 사고 대응

운영 중 데이터 일부 유실을 발견했을 때의 대응이 작업 방식을 잘 보여줍니다.

1. **즉시 복구** — 리비전 API + 시트 데이터 정합성 점검으로 유실분 복원
2. **재발 방지 가드 도입** — write 시 사용자/트리거/크기 변화를 best-effort로 남기는 **감사 로그**를 추가하되, *본 쓰기 동작은 차단하지 않도록* 비침습 설계
3. **외부 mutation은 고위험으로 분리** — 이슈 트래커 쓰기처럼 권한·비가역성이 있는 작업은 별도 승인·사용자 확인을 거침

## 결과 (Impact)

- 테스트 결과 공유 **30분 → 0분 (자동)**, Slack 알림으로 5분 내 대응
- 스프린트 단위 TC 실시간 현황 + GitHub 자동 동기화
- 통합 검증 프로세스 정착으로 **Critical 결함 41%↓** (Critical 버그 17건 → 10건), **배포 전 미해결 0건 · 처리율 100%** 유지
  *(출처: 스프린트별 품질 매트릭, 4개 스프린트 집계)*

## 사용 기술

`Google Apps Script` `GitHub Actions / Pages` `Allure` `Slack Webhook` `감사 로그(audit log)` `비파괴 데이터 모델`
